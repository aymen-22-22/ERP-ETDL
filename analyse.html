High-Level Architecture

Backend — Modular Monolith

FastAPI application with clear feature modules under app/. Cross-cutting shared code lives in app/shared/. Every module follows the same pattern:

  • models.py — SQLAlchemy ORM models
  • schemas.py — Pydantic request/response schemas
  • repository.py — Data access layer
  • service.py — Business logic
  • router.py — API route definitions

Key architectural decisions:

  • Postgres Row-Level Security for tenant isolation
  • Append-only ChangeLog ledger for all syncable writes
  • Async everywhere (asyncpg + SQLAlchemy async)
  • JWT auth with refresh token rotation
  • Dual entity hierarchy: SyncableMixin vs AuditMixin

Frontend — React PWA

React 19 single-page application with offline-first architecture:

  • React Router 8 for client-side routing
  • Zustand for auth state (in-memory only)
  • TanStack Query for mutation lifecycle
  • Dexie.js (IndexedDB) for offline local cache
  • Tailwind CSS 4 + Radix UI primitives
  • Vite + vite-plugin-pwa + Workbox
  • Zod + react-hook-form for form validation

Offline architecture: Reads from IndexedDB (Dexie), writes enqueue to a local mutation queue, which drains to the server when online. The server is always the source of truth.

Offline Sync Mechanism

Push Flow (Client → Server)

1. User submits a form (create/update/delete)
   ↓
2. Optimistic write to local Dexie table
   (UI updates instantly)
   ↓
3. enqueueMutation()
   - Generates clientMutationId (UUIDv7)
   - Creates QueuedMutation row in IndexedDB
   - Status: "pending"
   ↓
4. submitMutation()
   - Enqueues mutation
   - Calls runSync() immediately
   ↓
5. pushPending()
   - Reads next 100 pending mutations
   - POST /api/v1/sync/push
   ↓
6. Server: apply_mutations()
   For each mutation:
   - Check client_mutation_id (dedupe)
   - Look up repo in SYNC_REGISTRY
   - repo.apply_mutation():
     - Version check (optimistic concurrency)
     - _persist() to entity table
     - Append to ChangeLog (full server snapshot)
   - SAVEPOINT per mutation
   ↓
7. Results returned to client:
   - "applied"  → remove from queue
   - "duplicate" → remove from queue
   - "conflict" → mark conflicted, save server record

Pull Flow (Server → Client)

1. runSync() calls pullChanges() after push
   ↓
2. Read cursor from db.syncMeta ("sync_cursor")
   (0 on first run)
   ↓
3. GET /api/v1/sync/pull?since={cursor}&limit=200
   ↓
4. Server: build_pull_page()
   - SELECT from change_log WHERE tenant_id = ?
     AND server_seq > since
   - ORDER BY server_seq
   - LIMIT 201 (one extra for has_more)
   ↓
5. For each ChangeRecord:
   - applyChange():
     - If deleted_at ≠ null = tombstone → delete local
     - Else → upsert into Dexie table
   - Advance cursor
   ↓
6. Repeat if has_more == true
   ↓
7. Result: Local IndexedDB now matches server
   UI re-renders via liveQuery()

Key design decisions:
  • Idempotency keys (client_mutation_id) prevent double-apply from retried pushes
  • Optimistic concurrency via version field: push is rejected if base_version doesn't match server
  • Server is source of truth: conflicted writes are discarded, server record returned for reconciliation
  • SAVEPOINT isolation: one failing mutation doesn't block the batch
  • Full-server snapshots in ChangeLog let clients materialize any entity uniformly

Authorization Model 

User  ↔  UserTenantRole  ↔  Role  ↔  RolePermission  ↔  Permission  →  Code
     ↑
Tenant

A user can belong to multiple tenants (e.g. an accountant serving several businesses). Each membership carries a role which grants a set of permission codes. The require_permission("products:write") dependency factory checks this chain at runtime. Permission codes like products:read, products:write, inventory:read, inventory:write are seeded when their modules land.

DB-level tenant isolation: Postgres RLS policies use current_setting('app.tenant_id') set at the start of each request via get_tenant_db(). Even a bug in repository code can't leak cross-tenant rows.

Key Architectural Observations

Offline-First DNA

The sync framework is the central architectural decision. Every write path goes through SyncableRepository.apply_mutation() whether it arrives via REST or the offline queue. The ChangeLog is the single source of truth for replication. Client-generated UUIDv7 IDs mean offline creates never need a round-trip.

Modular Monolith, Not Microservices

The backend is a single FastAPI process with clear module boundaries. This avoids microservices complexity (network calls, distributed transactions, eventual consistency) while keeping code organized. The sync framework would allow extracting modules later if needed.

DB-Level Tenant Isolation

Postgres Row-Level Security is the last line of defense. Even if a bug in repository code forgets to filter by tenant_id, the RLS policy blocks cross-tenant data access. The app.tenant_id session variable is set at the start of each request.

Append-Only Inventory

Stock is never a directly editable column. Every change to on-hand quantity is an InventoryMovement row. Corrections use new offsetting movements, not edits to old ones. The ProductStockSnapshot is maintained transactionally alongside each movement.

PWA with Auto-Update

The service worker auto-updates with no user prompt (registerType: "autoUpdate" + immediate updateSW(true) on onNeedRefresh). Hourly periodic checks work around browser polling limitations. The app shell is cached via navigateFallback.

Security Patterns

Tokens stored in-memory only (not localStorage) to limit XSS theft. Argon2 password hashing. Refresh token rotation on each use. Rate limiting on login via Redis. Structured logging with structlog. Standardized error response envelope.
